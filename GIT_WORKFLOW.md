# 🔧 Git Workflow: Правила атомарных коммитов

## 📌 Золотое правило

**Один логический блок изменений = один атомарный коммит**

Для учебного курса действует уточнение:

> **1 файловый микро-шаг = 1 атомарный коммит.**

Если микро-шаг не изменил файлы репозитория, коммит не нужен.

---

## 🎯 Когда делать коммит

Коммит нужен после завершения каждой логической единицы работы, если изменились файлы репозитория:

- ✅ Написан и протестирован учебный скрипт в `learning/`
- ✅ Написан или обновлён тест
- ✅ Добавлена новая функция/модуль в `src/`
- ✅ Исправлена ошибка (bugfix)
- ✅ Обновлена документация репозитория (`README.md`, `COURSE_PLAN.md`, `LEARNING_JOURNAL.md`, `GLOSSARY.md`, docstrings)
- ✅ Изменена конфигурация (`requirements.txt`, `.gitignore`, `pyproject.toml`)
- ✅ Закрыта глава или крупный блок и обновлены соответствующие документы репозитория

Коммит не нужен, если:

- был только устный или теоретический разбор без изменения файлов;
- была диагностика без правки файлов;
- менялись только локальные файлы:
  - `mentor_prompt.md`;
  - `project_state.md`;
  - `flow.md`.

---

## 📝 Формат сообщений коммитов

Используем стиль **Conventional Commits**:

```text
<тип>(<область>): <краткое описание>
```

Опционально можно добавить тело коммита или ссылки, если это нужно.

### Типы коммитов

- `feat` — новая функциональность или новый учебный скрипт
- `fix` — исправление ошибки
- `docs` — изменения в документации
- `style` — форматирование, пробелы, стиль без изменения логики
- `refactor` — рефакторинг кода без изменения поведения
- `test` — добавление или изменение тестов
- `chore` — рутинные задачи: зависимости, конфигурация, служебные изменения

### Примеры

```text
feat(python): add list sorting methods
feat(ml-theory): add step 167 framing ml problems
fix(data): handle missing values in feature engineering
docs(readme): update current learning status
docs(course-plan): mark Huyen DMLS chapter 2 progress
test(classifier): add unit tests for wine classifier
chore(deps): update scikit-learn
```

---

## 🚫 Когда НЕ делать коммит

Не делай коммит:

- ❌ в процессе написания незавершённого кода;
- ❌ если код не запускался и не проверен;
- ❌ если изменения не относятся к репозиторию;
- ❌ если менялись только локальные файлы;
- ❌ с сообщением `update`, `fix`, `changes` без конкретики;
- ❌ с накоплением несвязанных изменений за несколько дней.

## 🔄 Процесс коммита

### 1. Проверить статус

```bash
git status
```

### 2. Добавить конкретные файлы

Добавляй только реально изменённые файлы репозитория.

Пример для учебного скрипта:

```bash
git add learning/02_ml_theory/step_167_framing_ml_problems.py
```

Пример для документации:

```bash
git add README.md
git add COURSE_PLAN.md
git add LEARNING_JOURNAL.md
git add GLOSSARY.md
```

### 3. Сделать коммит

```bash
git commit -m "feat(ml-theory): add step 167 framing ml problems"
```

### 4. Проверить историю

```bash
git log --oneline -5
```

### 5. Отправить на GitHub

```bash
git push origin main
```

---

## ⚠️ Правило для `git add .`

`git add .` **не используется по умолчанию**.

Предпочтительно добавлять файлы явно:

```bash
git add path/to/file.py
```

`git add .` допустим только если:

1. сначала выполнен `git status`;
2. Дмитрий убедился, что в индекс не попадут лишние файлы;
3. среди изменений нет локальных файлов:
   - `mentor_prompt.md`;
   - `project_state.md`;
   - `flow.md`;
4. нет временных файлов, кэша, артефактов IDE или окружения.

---

## 🧩 Формат команд в терминале

Правила:

- одна команда — одна строка;
- не объединять команды через `&&`;
- не объединять команды через `;`;
- перед `git add` всегда выполнять `git status`;
- все push выполняются явно в ветку `main`.

Правильно:

```bash
git status
git add learning/02_ml_theory/step_167_framing_ml_problems.py
git commit -m "feat(ml-theory): add step 167 framing ml problems"
git push origin main
```

Неправильно:

```bash
git add . && git commit -m "update" && git push
```

```bash
git add .; git commit -m "fix"; git push
```

## 📊 Частота коммитов

### Для учебных микро-шагов

**Правило:** 1 файловый микро-шаг = 1 атомарный коммит.

Коммит нужен, если микро-шаг изменил:

- учебный скрипт в `learning/`;
- тест;
- документацию репозитория;
- конфигурацию;
- файл данных или notebook, если они должны храниться в Git.

Коммит не нужен, если:

- был только теоретический разбор;
- было обсуждение ошибки без изменения файлов;
- менялись только локальные файлы:
  - `mentor_prompt.md`;
  - `project_state.md`;
  - `flow.md`.

### Для проектной работы

**Правило:** 1 логический блок изменений = 1 атомарный коммит.

Примеры логических блоков:

- модель обучена и сохранён код обучения;
- добавлен API endpoint;
- добавлен тест для API;
- исправлен конкретный bug;
- обновлена документация после закрытия главы.

Не смешивай в одном коммите:

- код и несвязанную документацию;
- несколько разных задач;
- исправление ошибки и новый функционал;
- локальные файлы и файлы репозитория.

---

## 🎓 Для учебного курса

После каждого файлового микро-шага:

1. Убедиться, что код работает.
2. Выполнить `git status`.
3. Добавить конкретный изменённый файл.
4. Сделать атомарный коммит.
5. Выполнить `git push origin main`.
6. Только после этого переходить к следующему учебному микро-шагу.

Если файловых изменений нет — коммит не нужен.

---

## 🌿 Ветка по умолчанию

Используем ветку:

```text
main
```

Все push выполняются явно:

```bash
git push origin main
```

Если нужно переименовать ветку в `main`:

```bash
git branch -M main
```

---

## 📁 Локальные файлы вне Git

Следующие файлы хранятся локально и **не коммитятся** в репозиторий:

| Файл | Назначение |
|---|---|
| `mentor_prompt.md` | системный промпт ментора |
| `project_state.md` | состояние проекта между сессиями |
| `flow.md` | инструкция запуска и закрытия сессий |

Эти файлы нужны только для управления сессиями с ментором и не являются частью портфолио.

Перед каждым коммитом проверяй:

```bash
git status
```

Если локальные файлы попали в список изменений, не добавляй их через `git add`.

---

## ✅ Чек-лист перед коммитом

Перед каждым коммитом проверь:

- [ ] Изменения относятся к репозиторию, а не к локальным файлам.
- [ ] Код запускается или изменение проверено вручную.
- [ ] Выполнен `git status`.
- [ ] В индекс добавлены только нужные файлы.
- [ ] Сообщение коммита конкретное и соответствует Conventional Commits.
- [ ] Локальные файлы `mentor_prompt.md`, `project_state.md`, `flow.md` не добавлены.
- [ ] Команды выполняются по одной строке.
- [ ] Push выполняется через `git push origin main`.
